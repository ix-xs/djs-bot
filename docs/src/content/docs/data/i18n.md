Three different things get called translation on a Discord bot, and each has
its own mechanism:

| What | Where it shows | How |
| --- | --- | --- |
| The messages your bot sends | Replies, embeds, buttons | `ctx.t()`, configured with `i18n` (this page) |
| Command names and descriptions | The command picker | `nameLocalizations` on the definition ([below](#command-names-and-descriptions)) |
| The messages the framework sends | Guard refusals, the generic error | `messages`, see [Wording and theme](/basics/wording-and-theme/) |

## A first translation

Declare one message tree per locale in `defineBot`:

```ts title="src/index.ts"
import { defineBot, env } from "@ix-xs/djs-bot";

export default defineBot({
  token: env("DISCORD_TOKEN"),
  features: "./features",
  i18n: {
    defaultLocale: "en",
    resources: {
      en: {
        daily: { claimed: "You claimed {amount} coins." },
        items: { one: "{count} item", other: "{count} items" },
      },
      fr: {
        daily: { claimed: "Vous avez reçu {amount} pièces." },
        items: { one: "{count} objet", other: "{count} objets" },
      },
    },
  },
});
```

Then call `ctx.t` in any interaction handler. Nested keys are written with
dots.

```ts title="features/economy/daily.command.ts"
import { defineCommand } from "@ix-xs/djs-bot";

export default defineCommand({
  name: "daily",
  description: "Claim your daily coins",
  run: async (ctx) => {
    // A French user reads "Vous avez reçu 100 pièces.", others the English string.
    return ctx.reply.success(ctx.t("daily.claimed", { amount: 100 }));
  },
});
```

`ctx.t` translates for `ctx.locale`, the language of the user's Discord client.
It is not the server's language: two people in the same server can get
different languages from the same command.

Without `i18n` in the configuration, `ctx.t(key)` returns the key. Handlers
written with `ctx.t` keep working, and adding translations later breaks
nothing.

## Variables and plurals

`{name}` placeholders are replaced from the second argument. Dotted paths reach
into objects.

```ts
// en: { greet: "Hello {name}", owner: "Owned by {owner.name}" }
ctx.t("greet", { name: ctx.user.username });   // "Hello Ada"
ctx.t("owner", { owner: { name: "Ada" } });    // "Owned by Ada"
ctx.t("greet", {});                            // "Hello "
ctx.t("greet");                                // "Hello {name}"
```

A variable that is missing from the object becomes an empty string. When no
object is passed at all, the text is returned as written, placeholders
included.

For a plural, give the key a `{ one, other }` pair and pass `count`:

```ts
// en: { items: { one: "{count} item", other: "{count} items" } }
ctx.t("items", { count: 1 });   // "1 item"
ctx.t("items", { count: 5 });   // "5 items"
ctx.t("items", { count: 0 });   // "0 items"
```

The rule is the same for every locale: `one` when `count` equals `1`, `other`
for everything else, including `0` and a missing `count`. Languages with more
plural forms than two need separate keys that you choose between yourself.

:::caution[Reserved key names]
Any object holding both a `one` and an `other` key is read as a plural pair.
Do not give those two names to a group of ordinary messages.
:::

## Locale fallback

Discord sends locales such as `"fr"`, `"en-US"`, `"en-GB"` or `"pt-BR"`. For
each key, the translator tries in order:

1. the exact locale, for example `"en-US"`
2. its base language, `"en"`
3. `fallbackLocale`, when set
4. `defaultLocale`
5. the key itself, returned unchanged

Step 2 is why resources keyed `en` cover both `en-US` and `en-GB`. The chain
runs per key, so a locale may be translated partially: the missing keys come
from the next step.

The last step means a missing translation degrades to a visible key such as
`ticket.opened`, not to a crash or an empty message. It is obvious in testing
and harmless in production. A key that points at a group of messages, not at a
message, counts as missing too.

## Translation files

`resources` is a plain object, so load it however you like. One JSON file per
locale keeps translators out of your code:

```ts title="src/locales/index.ts"
import en from "./en.json" with { type: "json" };
import fr from "./fr.json" with { type: "json" };

export const resources = { en, fr };
```

```ts title="src/index.ts"
import { defineBot, env } from "@ix-xs/djs-bot";
import { resources } from "./locales/index.js";

export default defineBot({
  token: env("DISCORD_TOKEN"),
  features: "./features",
  i18n: { defaultLocale: "en", resources },
});
```

## Outside interaction handlers

`ctx.t` exists where there is a user and therefore a locale: commands, context
menus, buttons, select menus, modals and autocomplete handlers. Events,
triggers and jobs have no `ctx.t`. There, and anywhere else (a service, a
scheduled announcement), build a translator with `createI18n` and pass the
locale yourself:

```ts title="src/i18n.ts"
import { createI18n } from "@ix-xs/djs-bot";
import { resources } from "./locales/index.js";

export const i18n = createI18n({ defaultLocale: "en", resources });

i18n.t("fr", "greet", { name: "Léa" });        // "Bonjour Léa"
i18n.t(undefined, "greet", { name: "Léa" });   // no locale: the default, "Hello Léa"
i18n.locales();                                // ["en", "fr"]
i18n.defaultLocale;                            // "en"
```

Pass the same `resources` object to `defineBot` and to `createI18n` so that
both read one set of messages.

## Command names and descriptions

What the user sees in the command picker is a different mechanism: Discord
translates it itself, from the `nameLocalizations` and
`descriptionLocalizations` declared on the command. It is independent of
`ctx.t` and works without `i18n`. It is described under
[Localized names](/commands/slash-commands/#localized-names).

A bot that is fully translated uses both: localized names so that a French
user types `/aide`, and `ctx.t()` so that the answer is in French too.

## Reference

### `I18nOptions`

The value of `i18n` in `defineBot`, and the argument of `createI18n`.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `resources` | `Record<string, Messages>` | required | Message trees, keyed by locale: `{ en: {...}, fr: {...} }`. |
| `defaultLocale` | `string` | `"en"` | The last locale tried before returning the key. Also `ctx.locale` when an interaction carries no locale. |
| `fallbackLocale` | `string` | none | A second locale tried before the default. |

### `Messages`

A nested tree of translations. Each value is one of:

| Value | Meaning |
| --- | --- |
| `string` | A message, with optional `{var}` placeholders. |
| `{ one: string; other: string }` | A plural pair, chosen from `vars.count`. |
| `Messages` | A group, reached with a dot in the key. |

### `ctx.t(key, vars?)`

```ts
ctx.t(key: string, vars?: Record<string, unknown>): string
```

Translates `key` for `ctx.locale` with the [fallback chain](#locale-fallback).
Returns the key when nothing matches or when `i18n` is not configured.

### `ctx.locale`

The user's Discord client locale, such as `"fr"` or `"en-US"`. When the
interaction carries none, it is the `defaultLocale`, or `"en"` without `i18n`.

### `createI18n(options)`

```ts
createI18n(options: I18nOptions): I18n
```

Creates a standalone translator. `defineBot({ i18n })` calls it for you.

### `I18n`

| Member | Type | Description |
| --- | --- | --- |
| `t(locale, key, vars?)` | `string` | Translates `key` for `locale` with the fallback chain. `locale` may be `undefined`. |
| `locales()` | `string[]` | Every locale that has resources. |
| `defaultLocale` | `string` | The configured default. |
